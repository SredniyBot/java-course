# ADR 004: композиция и владение состоянием, без JPMS

Статус: принято. Дата: 2026-09-21.

Контекст: все игры наследовали GamePanel, одновременно получая Swing API, очки, mutable Random и функции рисования. Связность была шире, чем необходимо.

Решение: финальный GamePanel — Swing-адаптер; он содержит DesktopGame и session-local GameSession. DesktopGame — маленький набор lifecycle/input callbacks, без DI-framework. GameDrawing — чистые операции на явно переданном Graphics2D. Gameplay state инкапсулирован внутри игры. Seed и клавиши не глобальны.

Наследование JPanel оставлено в одном адаптере: этого требует Swing. Чистые статические функции правил допускаются для маленьких задач. Вектор скорости и координата — records, а матрицы остаются массивами там, где цель — понять мутацию и aliasing. Не навязываем immutability сцене, обновляемой каждый кадр.

Maven modules дают отдельные build/test boundaries. JPMS с module-info.java регулирует exports/requires и runtime module path — это другой механизм. Здесь нет jlink, plugin isolation и необходимости скрывать пакеты между библиотеками; стоимость opens для тестирования пока выше пользы. JPMS не включён, отдельная тема курса может добавить его на конкретном примере.

Последствия: GameSession — намеренно ограниченный набор сервисов сессии; не расширять его до service locator. При росте одной игры выделяйте её собственную модель и порты, а не усложняйте общий интерфейс для остальных 24.
